# Build guardrails in code for a refund agent

Larkspur Home Goods is an online shop. It uses an agent to decide refund requests. Five tickets are waiting. One is a normal request. One is for an old order that is no longer in the live orders database. One has an instruction hidden in the customer's text. One asks for 1,200.00, which is more than the agent may refund. One comes from a customer whose account is only six days old. The agent can read the ticket and the order, and it can ask for a refund. Your job is to make sure the code, not the model, decides whether the money moves.

In this lab, you write four small functions in **lab.py**, which add up to about 21 lines of code. The lab takes about 30 minutes, and this guide gives you every line. At the end, the agent runs on all five tickets. Two refunds go through, and three requests go to a human queue.

This lab continues Demo 5B, so you will recognize the following:

- An agent with three tools: one to read the ticket, one to read the record, and one to issue the money.
- A fallback source that is used when the first source has no record, with a note that says where the answer came from.
- Customer text that is treated as untrusted data, not as an instruction.
- An approval limit that sits in code, and is not in the prompt.
- A human queue file for every request that the agent may not decide.

## Write the fallback lookup

The agent reads an order with the get_order tool. Most orders are in the live database. Some older orders were moved to an archive. In this section, you write the lookup that tries the live database first, then the archive, and says which one it used.

1. Open **lab.py** in your code editor.

2. Search for the comment **TODO 1 of 4 - THE FALLBACK LOOKUP**. Below it is the function `find_order`, and its only line is `raise NotImplementedError("TODO 1 is not done yet")  # replace this line in TODO 1`.

3. Replace that line with the following code. Keep the four-space indent:

    ```python
        order = core.lookup_orders(order_id)
        if order:
            return {"found": True, "source": "orders", "order": order, "note": "Read from the live orders database."}
        order = core.lookup_archive(order_id)
        if order:
            return {"found": True, "source": "archive", "order": order,
                    "note": f"Not in the live orders database. Read from the archive copy of {order['archived_on']}."}
        return {"found": False, "source": "none", "note": f"No record of {order_id}."}
    ```

4. Save the file, and then run `python check.py`.

5. Verify that the four lines under **TODO 1** show `[PASS]`.

    > **Note**: The note comes from your code, not from the model. It stays true even if the model forgets to mention the source.

## Write the approval check

This is the main guardrail. The model asks for a refund and gives an amount. Your function decides, in plain code, whether the refund goes ahead or a person decides. The model never sees this limit, and nothing in a ticket can change it.

1. In **lab.py**, search for the comment **TODO 3 of 4 - THE APPROVAL CHECK**. Below it is the function `check_refund(order, amount, policy)`, and its only line is `return "refund", []  # replace these lines in TODO 3`.

2. Replace that line with the following code. Keep the four-space indent:

    ```python
        reasons = []
        if amount > policy["agent_refund_limit"]:
            reasons.append(f"{amount:,.2f} is above the agent limit of {policy['agent_refund_limit']:,.2f}")
        if amount > order["total"]:
            reasons.append(f"{amount:,.2f} is above the order total of {order['total']:,.2f}")
        if order["customer_age_days"] < policy["new_customer_days"]:
            reasons.append(f"the customer account is only {order['customer_age_days']} days old")
        return ("human" if reasons else "refund"), reasons
    ```

3. Save the file, and then run `python check.py`.

4. Verify that the seven lines under **TODO 3** show `[PASS]`, and that the four lines under **The guard in the agent loop** show `[PASS]` for R-6001, R-6003, R-6004, and R-6005.

5. Review the check, noting the following details:

    - Each rule adds a reason when it finds a problem. The reasons are shown to the person who reviews the request.
    - A refund above 300.00 goes to a person, even when the order total is higher.
    - A refund of more than the order total goes to a person. This stops the 5,000.00 request hidden in ticket R-6003.
    - A customer account that is less than 30 days old goes to a person, even for a small amount.
    - No reasons means the verdict is `refund`. Any reason means the verdict is `human`.

    > **Note**: The checker uses a scripted model that is fully fooled. It asks for 5,000.00 on ticket R-6003, and your check still stops it. That is the test of a real guardrail: if the model were fully fooled, the rule would still hold.

## Add the escalation record

A request that goes to a person must be saved somewhere the person can find it. In this section, you write the function that adds one record to the human queue file.

1. In **lab.py**, search for the comment **TODO 4 of 4 - THE HUMAN QUEUE**. Below it is the function `add_to_queue(record, path)`, and its only line is `pass  # replace these lines in TODO 4`.

2. Replace that line with the following code. Keep the four-space indent:

